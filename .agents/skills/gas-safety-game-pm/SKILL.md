# Gas Safety Game PM

## Preflight

Read `knowledge/contest/official-rules.md`, `knowledge/contest/judging-rubric.md`, `knowledge/production/project-constraints.md`, `knowledge/game/webgame-standards.md`, and `knowledge/game/deliverable-contracts.md`. At project start, use the user's storyboard or concept as input; do not require an approved GDD before creating the brief. Read the approved GDD only after the design gate. Treat knowledge files as authoritative; do not copy changing contest facts into this skill.

## Product contract

Keep the default product a backend-free 2–3 minute browser game for touchscreen TV, tablet, and PC. Exclude accounts, personal data, online ranking, analytics SDKs, and paid dependencies unless the user explicitly expands scope.

Define one target audience, learning outcome, core loop, MVP, exclusions, supported devices, acceptance criteria, milestone owner, and evidence needed for completion. Set measurable playtest thresholds before testing. Maintain both deliverables: a one-minute first-round gameplay video and a self-contained HTML build for the second round. Decide whether the MVP is silent or assign rights-cleared font, sound, music, and voice work to the asset specialist.

## Gates

Use `Go / Revise / No-Go` with evidence, unresolved risk, next owner, and next artifact:

1. official eligibility and deliverables
2. verified learning objective
3. approved game design and MVP
4. G3a approved safety copy/placeholders, then G3b safety-approved interactive prototype
5. rights-cleared art and asset manifest
6. functional, accessible browser build
7. playtest comprehension
8. submission and execution readiness

Do not overrule Safety Reviewer, substitute PM judgment for UX or engineering evidence, or accept “implemented” without observable tests.
